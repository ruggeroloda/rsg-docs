## Change the theme
1. Commit in `theme/rsg_2022/` (`gitleaks git . --no-banner` = 0 findings before a push).
2. `./deploy.sh staging` → check the pages (`?cb=<ts>` dodges the cache; schema: Rich Results "Code" mode). Markup changes: `python3 checks/extractcheck.py OUT <staging URL> <live URL>` → no new trafilatura MISSING items vs live. Another chat may have uncommitted work in the tree: commit only your own hunks, deploy from a clean `git worktree add --detach ~/rsgdeploy <commit>` (never stash someone else's work).
3. `./deploy.sh live`. Only the commit last deployed to staging is accepted.
- What `deploy.sh` does: `git archive` (committed files only) → temp folder on the server → PHP lint 8.3 + 8.4 → change list → asks "yes" → syncs `rsg-core/` to `wp-content/plugins/rsg-core` and activates it, then the theme, with `--delay-updates --delete-delay` (all files swapped in one pass at the end) and `--delete` (**files not in git are removed: never copy anything to the theme folder by hand**, e.g. merchant logos go through the repo) → replaced/deleted files to `~/rsg_deploy_backups/<target>-<stamp>/` → tag `<target>-<stamp>` → clears WP Rocket minified copies + used CSS when PHP/CSS/JS changed → purge → live: a row in `rsg.change_log`. `--dry-run` lists only; `--no-purge` skips the purge.
- **Overwrite guard:** the server keeps the commit last deployed to each target in `~/rsg_deploy_state/{staging,live}.commit`; `deploy.sh` refuses when it isn't in HEAD's history (another chat's work: `git fetch origin --tags; git merge <id>` first); `--force` overrides. Two staging deploys seconds apart can still overwrite each other: after a staging deploy while another chat is active, `git fetch origin --tags` and check no newer `staging-*` tag appeared.
- Change log from a fresh device shell: run `ssh -i <hetzner key> -p 2222 -o StrictHostKeyChecking=accept-new ruggero@116.203.146.177 true` once first, else `deploy.sh` prints "change log not written".
- Rollback: deploy the previous `live-*` tag (or copy back from `~/rsg_deploy_backups/`). Never edit theme files on a server; deploys never touch the database or uploads. A staging purge **may** also clear live (shared site ID).

## Caches (outside in)
1. **Cloudflare edge:** HTML `s-maxage=2592000` (30 days), one copy for all countries (geo rule off since 11 Nov). Redirects not cached; REST `DYNAMIC`; sitemaps 60 s.
2. **WP Rocket** (kept, as Rocket.net recommends): page cache **off** (`wp-rocket-no-cache`) until the DFS purge also clears it (ROADMAP); **Remove Unused CSS on** (safelist h1–h6, `.rsg-dfs(.*)`, `.rsg-vh`, `.is-empty`, `.is-none`); **minify CSS + JS on** (copies in `wp-content/cache/min/`, not cleared by `rocket_clean_domain()`); delay JS, concatenation, preload and CDN off.
3. **Object Cache Pro** (Redis; db 0 = live, db 3 = staging; never bulk-scan it: `../hosting/RUNBOOK.md` Open 10).
- **Used CSS is per URL and keeps only selectors present when generated:** after a template change that adds classes or inline CSS, `wp eval 'rocket_clean_minify(); do_action("rocket_domain_options_changed");'` then purge. A used-CSS job submitted just before a deploy can complete with the old stylesheet: check `SELECT url,status,submitted_at FROM newguru_wp_wpr_rucss_used_css`, delete rows from before the deploy, purge. Phones get full stylesheets (no used CSS for mobile user agents).
- **Remove Unused CSS can't evaluate `:is()` or selector lists inside `:not()`** and drops complex pseudo-element rules: plain selectors, at most one simple `:not()`.
- Brand-family listings (`/reviews/<brand>/<family>/`) get no WP Rocket optimisation at all (cause unknown); `?cb=` renders are never optimised: check used CSS on the edge copy or with `curl --resolve www.runningshoesguru.com:443:127.0.0.1` from the server.
- Purge everything: `cd ~/public_html && wp eval 'rocket_clean_domain();' && wp cdn purge` (Claude may do this after a deploy). Who else purges: the DFS after each Amazon slot (≤ 4 a day), `deploy.sh`, Rocket.net's mu-plugin on post publish/update (that post's URLs only: publishing a newer review does not purge the old reviews' pages).
