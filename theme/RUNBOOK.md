## Change the theme
1. Commit in `theme/rsg_2022/` (`gitleaks git . --no-banner` = 0 findings before a push).
2. `./deploy.sh staging` → check the pages (`?cb=<ts>` dodges the cache; schema: Rich Results "Code" mode, staging is not crawlable).
   Markup changes: `python3 checks/extractcheck.py OUT <staging URL> <live URL>` for the sample reviews → no new trafilatura MISSING items vs live (15 Nov). Another chat may have uncommitted work in the same tree: commit only your own hunks and deploy from a clean `git worktree add --detach ~/rsgdeploy <commit>` (never stash someone else's work).
3. `./deploy.sh live`. Only the commit last deployed to staging is accepted.
- **Overwrite guard (18 Nov):** the server keeps the full id of the commit last deployed to each target in `~/rsg_deploy_state/{staging,live}.commit` (outside the web root). `deploy.sh` refuses when that commit is not in HEAD's history (another chat's work: `git fetch origin --tags; git merge <id>` first); `--force` overrides. A branch made before 18 Nov has the old `deploy.sh` without the guard: merge `main` first. deploy.sh finds the newest staging tag with `git for-each-ref --count=1` (22 Nov, `06ee5cb`): `git tag | head -1` under `pipefail` died of SIGPIPE (exit 141, no message) once there were ~276 tags.
- **Swap at the end (19 Nov, theme `d26aea5`, deploy.sh only):** the sync runs with `--delay-updates --delete-delay`: changed files go to hidden temp copies and are renamed in one quick pass at the end (before: file by file over 1–2 min, and a page loaded mid-deploy called a function whose file wasn't there yet: live fatal 19 Nov 15:27 UTC, `rsg_listing_filters()`, `rsg-php` red ~1 h). Tested on a scratch folder on the server (update, delete, protected files, backups, no `.~tmp~` left) and a staging dry run.
- `deploy.sh` also syncs `rsg-core/` to `wp-content/plugins/rsg-core` (own backup folder `plugin-rsg-core/`) and activates it, **before** the theme sync; `rsg-core/` never lands in the theme folder.
- What `deploy.sh` does: `git archive` (committed files only) → temp folder on the server → PHP lint 8.3 + 8.4 → shows the change list → asks "yes" → rsync with modes 755/644, keeping unchanged files' mtimes (asset `?ver=` depends on them) → replaced/deleted files saved to `~/rsg_deploy_backups/<target>-<stamp>/` → tag `<target>-<stamp>` → purge. `--dry-run` lists only; `--no-purge` skips the purge (the change shows after the next DFS purge: up to ~6.5 h, the longest gap is 20:15 → 02:45 UTC).
- Files listed in `.gitignore` (backups, logs, files with keys) are never uploaded or deleted.
- **Change log from a fresh device shell (20 Nov):** `deploy.sh` writes the live row over SSH with `BatchMode=yes`, so an unknown rsgmedia host key makes it print "change log not written". Run `ssh -i <hetzner key> -p 2222 -o StrictHostKeyChecking=accept-new ruggero@116.203.146.177 true` once first, or add the row by hand.
- After CSS/JS changes on live, `deploy.sh` itself runs `rocket_clean_minify(); do_action("rocket_domain_options_changed");` (minified copies + used CSS) before the purge. By hand: the same `wp eval`, then `wp eval 'rocket_clean_domain();' && wp cdn purge`.

## Caches (outside in)
1. **Cloudflare edge:** HTML `s-maxage=2592000` (30 days), one copy for all countries since the geo rule was switched off on 11 Nov (~08:45 UTC). Redirects are not cached; REST responses `DYNAMIC`.
2. **WP Rocket (kept, as Rocket.net recommends):** page cache **off** (`wp-rocket-no-cache`; to be switched on after DFS/theme/migration work, once the DFS purge also clears it). **Remove Unused CSS on** (safelist h1–h6, `.rsg-dfs(.*)`, `.rsg-vh`, `.is-empty`, `.is-none`), **minify CSS + JS on** (copies in `wp-content/cache/min/`, not cleared by `rocket_clean_domain()`); lazyload (WordPress does it), delay JS (decided: no), defer, concatenation, preload (Rocket.net: don't) and CDN (Rocket.net: skip; off since 11 Nov) off. `deploy.sh` clears the minified copies + used CSS itself when PHP/CSS/JS changes (live and staging, since 13 Nov).
3. **Object Cache Pro** (Redis, connected).
- **Used CSS is per URL and only keeps selectors present when it was generated**: after a template change that adds classes or inline CSS (not only CSS/JS files), clear it by hand: `wp eval 'rocket_clean_minify(); do_action("rocket_domain_options_changed");'` then purge (`deploy.sh` only does this for CSS/JS file changes). Staging runs Remove Unused CSS too (found 13 Nov; the old note said it didn't): `deploy.sh` clears minified copies + used CSS on **both** targets when PHP/CSS/JS changes, else staging checks show stale CSS. **A used-CSS job submitted shortly before a deploy can survive the clear and complete with the old stylesheet** (14 Nov, Cascadia 19): after a deploy check `SELECT url,status,submitted_at FROM newguru_wp_wpr_rucss_used_css` from the staging webroot; delete rows submitted before the deploy time, purge, revisit once (`wp cron event run --due-now` speeds up the queue on staging). `css/rsg-dfs.css` is printed inline and its `.rsg-dfs*` selectors are safelisted.
- **Remove Unused CSS can't evaluate `:is()` or selector lists inside `:not()`**: it drops such rules from the used CSS even when they match (14 Nov: the reskin's heading rule `:is(h1, h2, h3):not(.h4, .h5, .h6)` was missing, so headings fell back to the system font once used CSS existed; rewritten as `h1:not(.h4), …`). Complex pseudo-element rules (`a ~ b .c::before`) went too. Write theme CSS with plain selectors, one simple `:not()` at most, and check new rules in the used CSS (origin copy, see below) before go-live.
- **Brand-family listings (`/reviews/<brand>/<family>/`, 27 terms) get no WP Rocket optimisation at all**: no used CSS, no minified files, full stylesheets (live + staging, found 13 Nov; not a URI/cookie/query-string exclusion, not 404/search by the main query; cause unknown, next step `WP_ROCKET_DEBUG` on staging). Also: `?cb=` renders are never optimised (query string), so check used CSS on the edge copy or with `curl --resolve www.runningshoesguru.com:443:127.0.0.1` from the server.
- Purge everything: `cd ~/public_html && wp eval 'rocket_clean_domain();' && wp cdn purge` (Claude may do this after a deploy). Who purges today: the DFS after each Amazon slot (≤ 4 a day, `/rsg-dfs/v1/purge`), `deploy.sh`, and Rocket.net's mu-plugin on post publish/update (that post's URLs).
